# Aptos Swift SDK Audit Report (2026-02-21)

## Scope

- Repository: `aptos-labs/aptos-swift-sdk`
- Spec baseline: `aptos-labs/aptos-sdk-specs` (v1.0.0 docs)
- Audit types: **security**, **correctness**, **performance**

## Method

1. Static review of source and tests in `Sources/` and `Tests/`
2. Cross-check against spec requirements in:
   - `specifications/03-cryptography.md`

## Security Findings

### 1) Entropy generation failure is ignored in mnemonic generation (**High**)

- **Code:** `Sources/AptosSDK/Core/Crypto/Mnemonic.swift:80-85`
- **Issue:** `SecRandomCopyBytes` return status is ignored:
  - On failure, the function still returns the `Data(count:)` buffer (zero-initialized), producing predictable mnemonic entropy.
- **Spec impact:**
  - `03-cryptography.md` §8.1.1: mnemonic generation **MUST** use CSPRNG.
  - `03-cryptography.md` §10.1 and §10.5: key/mnemonic generation must not rely on predictable entropy.
- **Risk:** Predictable seed material if entropy API fails unexpectedly.

### 2) Fatal crash paths in crypto/auth key code (**Medium**)

- **Code:**
  - `Sources/AptosSDK/Core/Crypto/Secp256k1.swift:90-94`
  - `Sources/AptosSDK/Core/Crypto/AuthenticationKey.swift:27-30`
- **Issue:** `fatalError(...)` is used in library code paths.
- **Spec impact:** `08-error-handling.md` expects typed, recoverable error handling patterns.
- **Risk:** Process-level DoS instead of recoverable failure in host apps.

### 3) Keyless signing does not enforce JWT-expiry validity (**Medium**)

- **Code:** `Sources/AptosSDK/Advanced/KeylessAccount.swift:174-189`
- **Issue:** `sign(message:)` checks ephemeral key/proof expiry, but not `isJWTExpired`.
- **Spec impact:** `07-advanced-features.md` §5.10 defines validity checks including JWT expiration; §9.4 says JWT claims **MUST** be validated.
- **Risk:** Signing may proceed with stale identity token context.

## Correctness Findings

### 4) Keyless auth key derivation appears spec-incompatible (**High**)

- **Code:**
  - `Sources/AptosSDK/Advanced/KeylessAccount.swift:79-94`
  - `Sources/AptosSDK/Core/Crypto/AuthenticationKey.swift:35-40`
  - `Sources/AptosSDK/Core/Crypto/AuthenticationKey.swift:72-77`
- **Issue:** Keyless accounts derive address via `AuthenticationKey.fromSingleKey(...)` (scheme `singleKey = 0x02`) with `AnyPublicKey.keyless`.
- **Spec impact:** `04-accounts.md` / `07-advanced-features.md` define keyless scheme identifier `0x05` and a different derivation formula including issuer/audience/user fields.
- **Risk:** Non-interoperable keyless addresses/signatures vs spec-conforming SDKs.

### 5) Simulation uses Ed25519 signature variant for all `AnyPublicKey` types (**High**)

- **Code:** `Sources/AptosSDK/API/TransactionAPI.swift:223-228`
- **Issue:** For `signerPublicKey as? AnyPublicKey`, simulation always uses `.ed25519(zeroSig)` regardless of key variant (secp256k1/secp256r1/keyless).
- **Spec impact:** `06-api-clients.md` §4.5 simulation expects structurally valid authenticator/public-key pair.
- **Risk:** False failures or inconsistent simulation behavior for non-Ed25519 SingleKey accounts.

### 6) Multi-agent signer/address cardinality is not validated (**Medium**)

- **Code:** `Sources/AptosSDK/Advanced/MultiAgent.swift:43-78`
- **Issue:** No check that:
  - `secondarySigners.count == secondarySignerAddresses.count`
  - signer order/address alignment matches the address list
- **Spec impact:** `07-advanced-features.md` §3.6 requires equal lengths and ordered correspondence.
- **Risk:** Malformed authenticators produced client-side; avoidable submission failures.

### 7) MultiKey signature index validation missing; `totalKeys` ignored (**Medium**)

- **Code:** `Sources/AptosSDK/Core/Crypto/MultiKey.swift:62-79`
- **Issue:**
  - `totalKeys` parameter is unused.
  - duplicate/out-of-range indices are not rejected.
  - indices >= 32 silently drop bitmap bits due to `if byteIndex < 4`.
- **Spec impact:** `07-advanced-features.md` §9.1 requires unique, valid signer indices.
- **Risk:** Invalid signature sets can be constructed without local error.

### 8) Ed25519 private key parser does not accept 64-byte extended keys (**Medium**)

- **Code:** `Sources/AptosSDK/Core/Crypto/Ed25519.swift:75-87`
- **Issue:** `Ed25519PrivateKey.init(data:)` accepts only 32 bytes, and `fromHex` delegates to it.
- **Spec impact:** `03-cryptography.md` §2.3.3/§2.3.4 expects support for 64-byte extended Ed25519 private key forms.
- **Risk:** Spec non-compliance and interoperability gaps with SDKs/wallet exports using extended keys.

### 9) Derivation path parser does not accept `h` hardened notation (**Low**)

- **Code:** `Sources/AptosSDK/Core/Crypto/DerivationPath.swift:33-50`
- **Issue:** Hardened detection only supports `'` suffix.
- **Spec impact:** `04-accounts.md` §6.3.2 says parser **MUST** accept `'` or `h`.
- **Risk:** Rejection of valid derivation path notation used by some wallets/tools.

## Performance Findings

### 10) Recomputing BIP-39 lookup structures on every validation/parse (**Medium**)

- **Code:** `Sources/AptosSDK/Core/Crypto/Mnemonic.swift:45-46`, `119-126`
- **Issue:** `Set(BIP39Wordlist.words)` and a full word->index map are rebuilt on each call.
- **Impact:** Unnecessary repeated O(2048) setup allocations in hot paths (validation/import loops).
- **Recommendation:** Cache static `Set` and dictionary once.

### 11) LRU cache maintenance is O(n) per access/update (**Low-Medium**) 

- **Code:** `Sources/AptosSDK/Utils/Cache.swift:30-31`, `44-45`
- **Issue:** `accessOrder.removeAll { ... }` on every `get`/`set`.
- **Impact:** Degrades with larger cache sizes or high-frequency access patterns.
- **Recommendation:** Use linked-list + dictionary index/node references for O(1) touch/move.

### 12) Retry strategy parsing/path is brittle and misses max delay cap (**Low-Medium**)

- **Code:** `Sources/AptosSDK/Client/HTTPClient.swift:256-258`, `287-293`, `297-303`
- **Issue:**
  - `Retry-After` is parsed from synthesized error message text, not directly from response metadata.
  - No max-delay cap despite backoff recommendations.
- **Spec impact:** `06-api-clients.md` §9.3 recommends bounded retry behavior (default max delay guidance).
- **Impact:** Less predictable retry timing under rate-limit/server-failure conditions.

## Recommended Priority Fix Order

1. Fix mnemonic entropy status handling (Finding #1)
2. Fix simulation authenticator variant mismatch (Finding #5)
3. Align keyless auth derivation with spec (Finding #4) or document intentional deviation
4. Add strict multi-agent and multikey validation checks (Findings #6, #7)
5. Remove `fatalError` from library paths (Finding #2)
6. Apply performance cleanup for mnemonic lookup/cache/retry behavior (Findings #10-#12)
